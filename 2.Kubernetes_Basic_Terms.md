## 1. What is a Pod?

A Pod is the smallest deployable unit in Kubernetes. It defines how one or more containers should run.
Think of a Pod as a box that holds containers and provides them with shared networking and optional shared storage.

<img width="173" height="150" alt="image" src="https://github.com/user-attachments/assets/4e02c7d2-f60b-43a3-94e9-48a62bc3fc32" />

- A Pod specifies the containers, images, resource requirements, configuration, and other settings.
- A Pod usually contains one container, but it can contain multiple tightly coupled containers.
- Containers in the same Pod share a network namespace and can share storage through volumes.

Remember: A Pod is not itself a container; it is the Kubernetes unit used to deploy and manage containers.

## 2. What is a Kubernetes Cluster?

A Kubernetes cluster is a group of machines that work together to run and manage applications.
Imagine a company has several computers and wants to run its application across them. Kubernetes coordinates these machines.
<img width="552" height="620" alt="image" src="https://github.com/user-attachments/assets/818f2743-ae6c-40a8-be48-a3f12e48b581" />

- Control Plane: Makes decisions about scheduling and maintaining applications.
- Worker Nodes: Machines where application Pods run.
- Cluster: The Control Plane and Worker Nodes working together.
A node can be a virtual machine or a physical machine.

3. What is kubectl?
kubectl is the command-line tool used to communicate with a Kubernetes cluster.
Just as Docker has the docker CLI, Kubernetes has kubectl.


Remember: kubectl sends requests to the Kubernetes API Server, which processes them. It does not directly manage containers itself.

4. How do we access a Pod? What is ClusterIP?
Every Pod receives its own IP address from the cluster's networking setup. However, Pod IPs can change when Pods are replaced.
Kubernetes provides a Service to give applications a stable way to reach a set of Pods.
A Service of type ClusterIP gets a stable internal IP address that is reachable from within the cluster.

<img width="180" height="191" alt="image" src="https://github.com/user-attachments/assets/2e6557e4-2bbe-43ac-b4b4-c8ae981aaa98" />

For example, a Service might have the ClusterIP 10.96.0.10 and route traffic to matching application Pods.
Important distinctions:
- Pod IP: Address assigned to an individual Pod by the cluster networking setup.
- ClusterIP: Internal virtual IP assigned to a Service by Kubernetes.
- kube-proxy: Commonly implements Service traffic routing rules on nodes, but it does not assign the ClusterIP.
- CNI plugin: Provides Pod networking and assigns/configures Pod IP addresses.
A ClusterIP is generally accessible only from within the cluster. To expose an application externally, you can use options such as a LoadBalancer Service or an Ingress/Gateway setup.


5. What is a Deployment?
A Deployment manages a set of replicated Pods and helps keep the desired number of replicas running.
You can think of a Deployment as a manager responsible for ensuring that enough copies of your application exist.
A Deployment usually manages Pods through a ReplicaSet.

Suppose you want three copies of your application. You configure:

<img width="165" height="84" alt="image" src="https://github.com/user-attachments/assets/04ff2fc3-3542-4d93-81c2-7715ba26c840" />

Kubernetes works to maintain three replicas.
If one Pod disappears, the ReplicaSet creates a replacement to bring the number back to three.
Why not create a Pod directly?
A standalone Pod does not automatically recreate itself if it is deleted or fails permanently.
A Deployment provides useful capabilities such as:
- Self-healing: Replaces missing Pods through its ReplicaSet.
- Scaling: Lets you change the desired number of replicas.
- Rolling updates: Updates application versions in a controlled way.
- Rollback: Supports rolling back to a previous Deployment revision.
Horizontal Pod Autoscaling (HPA) can also adjust the Deployment's replica count based on configured metrics.
Important correction: A Deployment is often described informally as a wrapper around Pods, but technically it manages a ReplicaSet, which manages the Pods. A Deployment does not itself run the containers.
