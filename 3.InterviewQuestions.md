Q1. What is a Pod in Kubernetes?
Answer: A Pod is the smallest deployable unit in Kubernetes. It contains one or more containers that share the same network namespace and can share storage through configured volumes.
Key points:
- Each Pod has its own IP address.
- Containers inside a Pod share that network namespace and can communicate using localhost.
- Containers in the same Pod can use different ports, but cannot normally bind to the same IP, port and protocol simultaneously.
- Pod IPs are not guaranteed to remain the same after Pod replacement.
  
Q2. Why can a Pod contain multiple containers?
Answer: Multiple containers are placed in the same Pod when they are tightly coupled and need to share networking or storage.
Example: A main application container and a sidecar proxy in a service mesh.
Both containers share the Pod's network namespace and can access a common volume if one is mounted for them.

Q3. What is a Deployment, and why do we use it instead of creating Pods directly?
Answer: A Deployment manages application releases through ReplicaSets and supports declarative updates, rolling updates and rollbacks.
It also helps maintain the desired application replica count through its managed ReplicaSet.
For most long-running applications, creating Pods through a Deployment is preferable to managing standalone Pods directly.

Q4. What is a ReplicaSet?
Answer: A ReplicaSet ensures that the desired number of matching Pod replicas are running.
For example, if replicas: 3 is specified, the ReplicaSet attempts to maintain three Pods. If a Pod disappears, it creates a replacement.

Q5. If replicas: 3 is specified in a Deployment, does it mean three ReplicaSets?
Answer: No. It means three desired Pod replicas.
The usual initial structure is:
1 Deployment → 1 ReplicaSet → 3 Pods
During a rolling update, multiple ReplicaSets can coexist to manage old and new application versions.

Q6. What is the difference between a Deployment and a ReplicaSet?
Deployment	ReplicaSet
Manages application releases and rollouts	Maintains the desired number of Pods
Supports rolling updates and rollbacks	Creates replacement Pods when replicas are missing
Creates and manages ReplicaSets	Creates and manages matching Pods

Q7. What is a Kubernetes controller?
Answer: A controller continuously reconciles the actual cluster state with the desired state recorded in the Kubernetes API.
Example: If the desired replica count is three but only two Pods exist, the ReplicaSet controller attempts to create another Pod.

Q8. What is a Kubernetes Service?
Answer: A Service provides a stable network endpoint for accessing a group of Pods selected by labels.
It allows clients to access applications without tracking individual Pod IP addresses.
Key benefits:
- Stable virtual IP and DNS name.
- Service discovery.
- Traffic distribution across eligible endpoints.
- Support for exposing applications inside or outside the cluster, depending on the Service type.
  
Q9. What would happen if Kubernetes had no Service?
Answer: Applications would need another way to discover and track Pod addresses. Since Pod IPs can change after replacement, direct connections to individual Pod IPs would be difficult to maintain.
A Service provides a stable endpoint and updates its backend endpoint information as matching Pods change.

Q11. Can multiple containers run the same application on port 8080?
Answer: Yes. Multiple Pods can run the same application on port 8080 because each Pod has its own network namespace and IP address.
For example:
- Pod A: 10.1.0.5:8080
- Pod B: 10.1.0.6:8080
- Pod C: 10.1.0.7:8080
These are different network endpoints.
Two applications normally cannot bind to the same IP, port and protocol combination in the same network namespace.

Q12. Who decides which Pod receives incoming traffic?
Answer: A Service provides the stable endpoint. The EndpointSlice controller maintains endpoint information for matching Pods, while kube-proxy or an alternative networking data plane implements Service routing.
An Ingress controller or Gateway may additionally route external HTTP traffic based on hostnames, paths or other rules.
Traffic is not necessarily distributed equally or in round-robin order for every individual HTTP request.

Q13. What happens if a container crashes inside a Pod?
Answer: The kubelet manages the Pod's containers and attempts to restart a terminated container according to the Pod's restartPolicy.
For a Deployment-managed Pod, the policy is Always, so Kubernetes attempts to restart the container even if it terminated successfully.
The Pod may retain its identity and IP when only its container restarts.

Q14. What happens if an entire Pod disappears?
Answer: The ReplicaSet detects that the actual number of matching Pods is below the desired replica count and attempts to create a replacement Pod.
The replacement runs a new container instance from the specified image. It is not the same running container being transferred to another Pod.

Q15. Where is restartPolicy defined?
Answer: It is a Pod-level setting. In a Deployment, it is specified inside spec.template.spec.
Common policies:
- Always: Restart terminated containers.
- OnFailure: Restart containers that terminate unsuccessfully.
- Never: Do not automatically restart terminated containers.
For ordinary application Pods managed by a Deployment, restartPolicy must be Always.

Q16. What is the difference between liveness and readiness probes?
Answer: A liveness probe helps Kubernetes determine whether a container should be restarted. A readiness probe helps determine whether a Pod should receive Service traffic.

Q17. Who checks whether a Pod is healthy before routing traffic?
Answer: There is no fresh health check for every incoming request.
The kubelet executes configured probes and updates Pod status. The EndpointSlice controller maintains endpoint information, including readiness conditions. The Service networking data plane uses that information to route traffic.
A readiness probe is not a guarantee that every subsequent request will succeed.

Q18. What are the Pod lifecycle phases?
Answer: The main Pod phases are:
- Pending: Pod accepted, but setup or container startup is not complete.
- Running: Pod is bound to a node and its containers have been created; at least one is running or starting/restarting.
- Succeeded: All containers terminated successfully and will not restart.
- Failed: All containers have terminated, with at least one unsuccessful termination.
- Unknown: Kubernetes cannot determine the Pod's state.
A Pod can be Running but not Ready.

Q19. What are the container lifecycle states?
Answer:
- Waiting: The container is waiting to start or proceed with startup.
- Running: The container is executing.
- Terminated: The container has stopped, either successfully or unsuccessfully.
These states are different from the Pod lifecycle phases.

Q20. What is the difference between application logs, container logs and file-based logs?
Answer:
- Application logs: Messages generated by the application, such as Spring Boot errors.
- Container logs: Commonly, the process output captured from stdout and stderr, accessible through commands such as kubectl logs.
- File-based logs: Logs written to files, such as /app/logs/application.log.
Application logs can be emitted to either standard output/error or files. The terms describe different aspects of logging, not necessarily different messages.

Q21. How can logs be retained after a Pod is deleted?
Answer: Production systems commonly send application output to a centralized logging system using a log collector.
Examples include Elasticsearch, OpenSearch and CloudWatch.
Persistent storage can also retain file-based logs if the application writes to a mounted persistent volume. Centralized logging is generally preferable for operational logs and root-cause analysis.

Q22. What is the difference between container restart and Pod replacement?
Answer: A container restart occurs inside an existing Pod and may preserve the Pod IP. Pod replacement creates a new Pod and new container instance, normally with a new Pod IP.
The kubelet handles container lifecycle management; the ReplicaSet maintains the desired number of Pods.
